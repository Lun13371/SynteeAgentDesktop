# Мини-агенты, контекст и стоимость в 1.1.6

## Найденные причины

- Первое значение контекста считалось до обработки вложений и не учитывало фактический каталог MCP. После ответа API интерфейс мог показывать резко выросшее значение. Теперь начальная оценка использует отправляемые сообщения, reasoning и все схемы инструментов. Свежая оценка после сжатия заменяет прежний usage без подмены её «реальными» данными API.
- Текстовые вложения до 5 МБ целиком попадали в prompt. Теперь общий бюджет превью ограничен 16 тысячами токенов и 8% окна модели, отдельного файла — 8 тысячами. Модель получает начало, конец и путь к исходнику для целевого чтения.
- Сжатие Janitor могло пропадать при следующем запросе. Восстанавливаются применённые summaries по идентификаторам вызовов; оригиналы доступны через постраничный `recall_context`. Уникальные результаты остаются в БД. Архив ограничен 50 записями и 4 млн символов; заполнение архива не приводит к удалению новых уникальных данных.
- `slice(-0)` включал полный MCP output в summary. Также исправлены границы секций `read_files`, сохранение уникальных секций, регистр POSIX-путей, дедуп меняющихся результатов и соблюдение выключенного Janitor.
- Служебные события могли запускать локальную модель без потребности в генерации. Очередь теперь имеет отмену и предел ожидания, возобновляется после восстановления сервера, отбрасывает ответы старых запусков. Архивирование памяти после завершения сохранено.
- Кеш на 200 эмбеддингов не вмещал каталог из 488 инструментов. В проверке повторного прохода число расчётов сократилось с 489 до 1. Это измерение работы кеша, а не обещание такого же ускорения всего ответа.

## Что означает цена

Прежняя сумма жила в отдельном worker и терялась после его завершения. Расходы субагентов и фоновых текстовых вызовов не попадали в неё. Кешированные токены могли считаться бесплатными при неизвестной цене кеша.

Новый журнал в SQLite учитывает SDK-запросы основного агента, субагентов и фоновой текстовой обработки. Идентификатор запроса предотвращает двойное начисление при нескольких пакетах usage. Промежуточные данные обновляются итоговыми. Сумма сохраняется между запусками приложения. В журнал не пишутся prompts, ответы или ключи API.

Цена чата остаётся **тарифной оценкой по usage API**, а не подтверждённым списанием Gateway. Неизвестный тариф, отсутствующий usage и принудительная остановка отмечаются как неполный учёт. При неизвестном тарифе кеша используется обычная цена входа; бесплатный кеш допустим только при явном нулевом тарифе. Для Gateway не подставляется цена похожей по имени публичной модели.

Панель отдельно показывает серверный расход **всего аккаунта Syntee за последние 24 часа**, полученный при её открытии и кешируемый на 30 секунд. Он включает другие чаты и устройства, поэтому его нельзя выдавать за цену выбранного чата. Нетокенные медиа-запросы и расходы без доступного usage следует сверять с серверной статистикой. Исторические расходы до установки 1.1.6 задним числом не восстанавливаются.

## Проверка и границы

Регрессионные проверки используют локальные SDK-фикстуры и временные БД/профили без запросов к платным моделям. Проверяются отмена, параллельные чаты, восстановление очереди, кеш эмбеддингов, дедуп начислений, цены кеша, сохранение после перезапуска, восстановление оригиналов Janitor и большие вложения.

82 профильных теста, включая проверки целей, проходят на Windows и Arch/WSL2. Для тестов целей обновлены устаревшие заглушки. В полном Windows-наборе проходят 229 из 235 тестов; шесть оставшихся падений относятся к прежним task-summary/delegation проверкам. Отдельные проверки worker, Code Mode, MCP и миграций проходят на обеих платформах. Пакет 1.1.6-1 установлен через pacman в Arch/WSL2; `pacman -Qkk` сообщает 1949 файлов и 0 изменённых.

Панель стоимости проверена в браузере с тестовыми данными. Запуск изолированного готового Windows-приложения для нового end-to-end сценария отклонён автоматическим контролем выполнения; этот сценарий не заявляется пройденным. Проверка AI worker в Electron, QuickJS и SQLite проводится отдельно без запуска чата и обращения к провайдерам.

В исходном проекте остаются известные падения общих тестов и ошибки полного TypeScript-check. Успешные профильные проверки не означают отсутствие всех ошибок в приложении. В частности, заявленное Gateway окно контекста может отличаться от фактического ограничения маршрута; этот серверный лимит требует проверки отдельно.
