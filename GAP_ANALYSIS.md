# Gap-анализ: Syntee Helper vs Claude Code / Codex CLI / OpenCode

> Аудит через параллельные subagent-исследования `src/core/agent`, `src/core/tools`,
> `src/core/context`, `src/core/memory`, `src/core/tokens`, `src/core/db`, `src/core/ai`,
> `src/core/prompts`, `src/main`, `src/renderer`, перепроверенный по официальной документации
> Claude Code (tools-reference, hooks, checkpointing, agent-view, sandboxing, costs/prompt-caching,
> sub-agents) — чтобы не приписывать конкурентам функционал, которого у них тоже нет.
>
> Легенда статусов: `[ ]` не начато · `[~]` в работе · `[x]` сделано.
> Второй проход (проверка фактов): 2026-07-20.

---

## 1. Критично — подтверждено документацией, реально есть у Claude Code

- [ ] **Нет пост-эдит верификации через LSP.** У Claude Code это официальный built-in tool
  `LSP` — "Code intelligence via language servers: jump to definitions, find references,
  report type errors and warnings". У нас `edit_file`/`write_file`/`multi_edit_file`
  (`tools/index.ts`) просто пишут на диск и отдают diff — 0 совпадений по
  `diagnostic|tsserver|lsp` в коде. Модель должна сама догадаться вызвать `run_command npm run
  build`, ничего не enforced.
  → Добавить tool `get_diagnostics`: либо реальный LSP-клиент (tsserver для TS, pyright для
  Python и т.д.), либо на первом шаге проще — обёртка над `tsc --noEmit`/`eslint --format json`,
  парсинг в структурированный список ошибок с file:line.

- [ ] **Нет системы hooks (жизненный цикл агента).** У Claude Code это отдельная развитая
  подсистема: `PreToolUse`/`PostToolUse`/`Stop`/`SessionStart` и т.д. — пользовательские shell-
  команды/HTTP/MCP-tool/LLM-prompt хендлеры, которые можно вешать на конкретные тулы (matcher
  `Edit|Write`) и получать structured JSON-решение (allow/deny/доп. контекст). Именно через
  `PostToolUse`-hook там реализуется "прогнать тесты после правки" — **не отдельным tool'ом**.
  У нас такого механизма нет вообще (0 совпадений по `preToolCall|postToolCall`). Есть только
  generic `run_command`, вызываемый по решению модели.
  → Минимально: настраиваемая "команда проверки" в Settings проекта (например `npm test`),
  автоматически запускаемая после N-й правки файла, результат подмешивается в контекст —
  упрощённый аналог `PostToolUse`-хука без полной hook-инфраструктуры.

- [ ] **Нет persistent shell-сессии.** У Claude Code Bash tool сохраняет состояние процесса
  между вызовами внутри одной сессии. У нас каждый `run_command` (`tools/index.ts:72-142`) —
  новый `exec()`/PowerShell-процесс с нуля. `cd`, активированный venv, экспортированные
  переменные не переживают между вызовами (сохраняется только `Agent.workdir` — рабочая
  директория чата на уровне приложения, не реальный shell state).
  → Держать один живой shell-процесс на чат/агента, посылать команды через stdin, читать вывод
  до уникального маркера конца команды.

- [ ] **Нет prompt caching.** У Claude Code это включено **автоматически** для всех сессий и
  прямо экономит деньги/скорость на длинных диалогах (кэшируется статичный префикс — system
  prompt, инструменты, project context). У нас `cache_control` не используется ни в одном
  запросе, хотя `cacheReadPerM`/`cacheWritePerM` уже парсятся из каталога моделей models.dev,
  но никуда не идут — инфраструктура наполовину готова, просадка по цене реальна на каждом чате.
  → Добавить `cache_control: {type: 'ephemeral'}` на статичный префикс system prompt при работе
  через Anthropic-совместимый эндпоинт. Самый дёшево реализуемый пункт из всего списка.

## 2. Существенно — архитектурные пробелы, тоже подтверждённые у конкурента

- [ ] **Нет checkpoint/rewind сессии.** У Claude Code это зрелая, давно обкатанная фича:
  `/rewind` (или двойной `Esc`) открывает меню по каждому промпту сессии, хранит до 100
  последних чекпоинтов с file-снапшотами, позволяет restore code / restore conversation /
  оба сразу, либо "summarize from/up to here" для сжатия части истории без потери файлов.
  Ограничение даже у них — bash-команды (`rm`, `mv`, `cp`) не трекаются, только правки через
  file-tools. У нас есть только rolling-window компакция контекста (`contextManager.ts`), нет
  снапшота состояния файлов для откат на произвольный шаг разговора. 0 совпадений по
  `checkpoint|rollback` (кроме `revert_last_change`, который про последнюю правку файла, не
  историю диалога).
  → Хранить file-снапшот (что изменено + до/после) на каждый пользовательский промпт,
  UI-кнопка "откатиться сюда", восстанавливающая и диалог, и файлы.

- [ ] **Нет multi-session оркестрации.** У Claude Code это отдельный полноценный режим
  (`claude agents` — Agent View): экран со всеми фоновыми сессиями сразу, dispatch новой задачи
  без остановки текущей, peek/reply без входа в сессию, группировка по статусу (working/needs
  input/completed), сессии продолжают работать в фоне даже с закрытым терминалом. У нас
  `activeRun` в `chat.ipc.ts` — module-level переменная, только **один** активный стриминг на
  всё приложение; новый `chat:send` вытесняет предыдущий, даже если это другой чат.
  → Минимально: переход на map `chatId → activeRun`, разрешить параллельный стриминг в разных
  чатах. Полноценный "agent view"-экран — отдельная амбициозная фича, не MVP-приоритет.

- [ ] **Нет git worktree изоляции для суб-агентов.** У Claude Code это опциональная, но
  встроенная возможность: фоновые сессии (agent view) **автоматически** переезжают в
  `.claude/worktrees/` перед первой правкой файла; обычные Task-суб-агенты — по явному
  `isolation: worktree` в конфиге (не включено по умолчанию для простого делегирования). У нас
  `spawn_agent` вообще не передаёт отдельный `workdir` — все параллельные суб-агенты пишут в
  общую файловую систему без какой-либо изоляции, риск гонок при параллельной записи одних и тех
  же файлов реален и никак не митигирован — это хуже даже дефолтного поведения Claude Code.
  → На каждый **параллельный** (не последовательный) суб-агент — свой `git worktree add`,
  слияние изменений в конце.

- [ ] **Нет AGENTS.md/CLAUDE.md-конвенции проекта.** У Claude Code `CLAUDE.md` в корне
  репозитория — файл, который коммитится в git, автоматически подхватывается при открытии
  проекта и содержит project-specific инструкции (стиль кода, команды сборки/теста, архитектурные
  решения) — команда делится этим со всеми через репозиторий. У нас кастомный system prompt —
  глобальная настройка приложения (`store.modelParams.systemPrompt`), не файл в репозитории.
  → При `analyze_project`/открытии чата искать `AGENTS.md`/`CLAUDE.md`/`.syntee/instructions.md`
  в корне workdir и подмешивать в системный промпт.

- [ ] **Нет кастомных slash-команд/skills.** У Claude Code — `.claude/commands/*.md` (кастомные
  команды) и полноценные **Skills** (переиспользуемые prompt-based workflow'ы с собственным
  frontmatter, инструментами, подгружаемые on-demand через `Skill` tool) — обе штуки можно
  коммитить в репозиторий и делить с командой. У нас `SLASH_COMMANDS` в `shared/slashCommands.ts`
  — статичный список из 7 захардкоженных команд, нет загрузки пользовательских файлов.
  → Сканировать `.syntee/commands/*.md` в проекте, регистрировать динамически.

- [ ] **Vision не интегрирован как нативный мультимодальный вход.** У Claude Code картинки —
  это просто аргумент обычного `Read`-тула (модель сама мультимодальная, видит вставленный
  скриншот прямо в диалоге, без отдельного "vision-вызова"). У нас `AIClient.analyzeImage()`
  — отдельный одноразовый вызов под выделенную роль `vision` (не встроен в основной
  tool-calling цикл `chatWithTools`), агент сам не может попросить проанализировать файл-картинку
  по ходу обычного диалога — только через отдельную Overlay-фичу.
  → Добавить tool `analyze_image(path)`, диспетчеризовать в `Agent.executeTool`, либо (лучше,
  если модель поддерживает vision нативно) прокидывать картинку прямо в `chatWithTools` как
  image-content-block, без отдельного vision-провайдера.

- [ ] **Нет MCP (Model Context Protocol).** Ни серверов, ни кастомных пользовательских tools.
  0 совпадений в коде. MCP — основной способ, которым Claude Code расширяется сторонними
  интеграциями (`.mcp.json`, `mcp__server__tool` naming, тулы от сервера подгружаются в
  контекст on-demand).
  → Минимально: MCP client в `AgentManager`/`Agent.ts`, конфиг серверов в Settings,
  динамическая регистрация их tools в `TOOL_SCHEMAS`.

## 3. Не гэп, снято/понижено после проверки фактов (было неточно в первой версии)

- ~~**RAG/семантический поиск по коду.**~~ У Claude Code **тоже нет** vector-embedding RAG по
  умолчанию — поиск идёт через `Grep`/`Glob` + опциональный `LSP`-tool (символьная навигация,
  не эмбеддинги) + опциональные "code intelligence plugins" от команды. Наше отсутствие
  `embed()`-использования — не гэп относительно Claude Code, это просто мёртвый код
  (`AIClient.embed()` нигде не вызывается). Решение: либо вырезать как мёртвый код, либо
  оставить как самостоятельное (не "погоня за паритетом") улучшение поиска — низкий приоритет.

- ~~**Декларативный workflow/DAG-оркестратор.**~~ У Claude Code тоже нет графа
  задач/DAG-исполнителя — многоагентность там тоже ad-hoc (Task tool по требованию модели,
  либо Agent Teams — параллельные "тиммейты", общающиеся сообщениями, но без формального графа
  зависимостей/retry/условных переходов). Наш `spawn_agent` + `/agent`-инструкция в системном
  промпте — концептуально то же самое. Не гэп относительно Claude Code; workflow-DAG — фича
  уровня "выше паритета", не приоритет для догона.

- ~~**OS-level sandbox для run_command.**~~ У Claude Code sandbox (Seatbelt/bubblewrap) в принципе
  **не работает на native Windows** — только macOS/Linux/WSL2. Раз Syntee Helper — Electron-
  приложение, ориентированное на Windows, здесь паритет, а не гэп: у конкурента на нашей целевой
  платформе та же ситуация (либо WSL2, либо эвристический regex-guard, как у нас через
  `commandSafety.ts`). Blacklist-only остаётся честным техническим долгом (см. раздел 4), но не
  критичным пунктом "догоняем Claude Code".

## 4. Второстепенно — полировка (не завязано на сравнение с конкурентами)

- [ ] **Sandbox только blacklist, не whitelist.** `forbiddenPaths` (`commandSafety.ts`) —
  список запрещённых путей, но нет режима "разрешено только внутри workdir проекта"
  (workspace jail). Модель по умолчанию может писать за пределы проекта, если явно не запрещено.
- [ ] **`edit_file` без unified-diff как входного формата.** Свой SEARCH/REPLACE-блочный формат
  (`applySearchReplacePatch`), не совместим со стандартным unified diff/patch.
- [ ] **Нет межфайловой атомарности правок.** Если 2-й из 3 файлов в серии `edit_file`-вызовов
  падает, 1-й остаётся изменённым — нет "commit/rollback всех правок сразу".
- [ ] **Wake-word в голосовом режиме не подключён.** `wakeWord` есть в настройках
  (`constants.ts:42`), анимация трея есть (`TrayManager.startListeningAnimation`), но реального
  распознавателя (porcupine и т.п.) нет — мёртвая настройка.
- [ ] **Spotlight — UI-скелет с мок-данными.** `getSearchResults()` в `SpotlightPage.tsx` —
  статичный список без реального fuzzy-поиска по функциям/файлам/командам.
- [ ] **3 из 8 задекларированных хоткеев не реализованы.** `readAloud (Alt+R)`, `translate (Alt+T)`,
  `screenshot (Alt+S)` есть в `constants.ts`, но не подключены в `HotkeyManager` bindings.

## 5. Что уже на уровне конкурентов (не трогать без причины)

- Todo-list/sub-agent spawning/planning mode — полная реализация (`update_todo`, `spawn_agent`,
  `save_plan`), сравнимо с Claude Code TodoWrite/Task tool.
- Context compaction — двухуровневая (LLM-summary rolling window + аварийная обрезка старых
  раундов), архитектурно не хуже Claude Code (хотя без rewind-механизма поверх — см. раздел 2).
- Permissions/approval — эвристический regex-guard (auto/ask/full) + `forbiddenPaths`,
  концептуально близко к Codex CLI approval modes.
- Многопровайдерность AI — 11+ провайдеров включая Ollama, ролевой роутинг по задачам,
  стриминг, tool use — зрело реализовано.
- Git через generic `run_command` — паритет с Claude Code (там тоже нет отдельных git-тулов).
- Overlay (screen-capture + vision анализ) — фича, которой нет у терминальных конкурентов
  (Claude Code/Codex CLI/OpenCode), реальное отличие в плюс.
